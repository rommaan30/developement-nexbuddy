1. FEATURE OVERVIEW
================================================================================

1.1 Why This Feature Exists
---------------------------
Website visitors chat with an embedded AI chatbot. Those conversations often
contain commercial intent and contact details (email, phone, company, interest).
Previously, that information lived only inside raw chat history rows
(`ext_chatbot_histories`). Sales / support staff had to open conversations
manually and scan messages.

AI Bot Enquiries automatically:

  • Detects qualifying lead signals from user messages
  • Scores the lead
  • Persists structured enquiry records
  • Surfaces them in:
      - Sidebar menu: "AI Bot Enquiries"
      - Dedicated listing page
      - AI Chat Bots dashboard analytics
      - Messages drawer "Extracted Enquiry" card

1.2 Business Requirement
------------------------
Capture chatbot leads without requiring a separate lead form.

Expected product outcomes:

  • Every qualifying visitor message flow creates (or skips, if duplicate)
    a structured enquiry
  • Admins can filter, sort, update status/notes, open conversation, delete
  • Dashboard shows counts and latest leads
  • Messages UI shows extracted enquiry for the conversation (HasOne view)

1.3 Problem Statement
---------------------
Chat transcripts are unstructured text. Without extraction:

  • Leads are easy to miss
  • No lead score
  • No status pipeline (new / contacted / qualified / closed)
  • No centralized enquiry list across owned chatbots

1.4 Expected Behaviour (As Implemented)
---------------------------------------
WHEN a visitor sends a user-role message through the chatbot API
AND ChatbotHistory is created with role = "user"
THEN ChatbotHistory::booted() created hook runs detectAndStoreEnquiry()
AND EnquiryDetectorService analyses candidate user messages
AND if lead_score >= 50 AND not a duplicate of email+phone+interest
THEN a new row is inserted into ext_chatbot_enquiries
AND the enquiry appears on the AI Bot Enquiries page for the chatbot owner

Additional behaviours that exist:

  • Multiple distinct enquiries can exist for one conversation
  • Exact same email+phone+interest combination in the same conversation is
    treated as duplicate and skipped
  • Detection failures are logged as warnings; chat message flow continues
  • Deleting an enquiry deletes only the enquiry row (not conversation/history)
  • After delete, a later qualifying user message can create a new enquiry again

  Why: customer deletion should not destroy enquiry history; set null

4.4 Indexes

  - Primary key on id
  - Foreign key indexes (Laravel foreignId convention)

There is NO unique index on conversation_id.

4.5 Column-by-Column Usage
--------------------------

chatbot_id
  Required: YES (FK, not nullable)
  How used: Ownership scoping in controllers:
            whereIn('chatbot_id', auth()->user()->externalChatbots()->pluck('id'))
  How queried: index filters, dashboard counts, destroy/update ownership checks
  Set on create from: $conversation->chatbot_id

conversation_id
  Required: YES
  How used: Link to chat; Open Conversation button; multi-enquiry grouping
  How queried: conversation->enquiries(), HasOne enquiry() for Messages UI
  Set on create via: $conversation->enquiries()->create(...) which sets FK

chatbot_customer_id
  Required: NO
  How used: Display customer name in listing via with('customer:...')
  Set on create from: $conversation->chatbot_customer_id

email / phone / company / interest
  Required: NO individually
  How used: Display, search filters, duplicate comparison (email+phone+interest)
  Source: EnquiryDetectorService detect() output

lead_score
  Required: YES (default 0)
  How used: Filters 0-49 / 50-79 / 80-100; sorting by lead_score; UI badges
  Source: LeadScorer; only rows with score >= 50 are created by detection path

status
  Required: YES (default 'new')
  Allowed in controller validation: new, contacted, qualified, closed
  How used: Filter, analytics groupBy, badge colours

notes
  Required: NO
  Max length on update validation: 5000
  How used: Admin internal notes on listing page

6. COMPLETE EXECUTION FLOW
================================================================================

This section traces the full path from visitor message to dashboard display.

--------------------------------------------------------------------------------
STEP 1 — User Types Message In Widget / Test Page
--------------------------------------------------------------------------------
Actor   : Website visitor or tester
UI      : Embedded chatbot widget OR resources/views/chatbot-test.blade.php
Purpose : Capture free-text prompt (and optional media)

--------------------------------------------------------------------------------
STEP 2 — Widget Sends HTTP Request
--------------------------------------------------------------------------------
Method  : POST
Route   : api/v2/chatbot/{chatbot:uuid}/session/{sessionId}/conversation/{chatbotConversation}/messages
Name    : api.v2.chatbot.conversion.store.message
File    : ChatbotServiceProvider.php (API group)
Middleware: api, LanguageMiddleware

--------------------------------------------------------------------------------
STEP 3 — Controller Receives Request
--------------------------------------------------------------------------------
File    : app/Extensions/Chatbot/System/Http/Controllers/Api/ChatbotApplicationController.php
Method  : storeMessage(ChatbotHistoryStoreRequest $request, Chatbot $chatbot,
            string $sessionId, ChatbotConversation $chatbotConversation)
Purpose :
  - Validate conversation belongs to chatbot and session
  - Optional media upload
  - Call insertMessage(..., role: 'user', ...)
  - Generate AI response (unless agent connected)
  - Insert assistant message

--------------------------------------------------------------------------------
STEP 4 — Conversation Validated / Retrieved
--------------------------------------------------------------------------------
Already route-model-bound as $chatbotConversation.
Additional checks abort(404) if chatbot_id or session_id mismatch.

--------------------------------------------------------------------------------
STEP 5 — History Stored (User Message)
--------------------------------------------------------------------------------
File/Method: ChatbotApplicationController::insertMessage()
Action     : ChatbotHistory::query()->create([... role => $role ...])
Table      : ext_chatbot_histories
Result     : New ChatbotHistory model instance returned

Also updates conversation last_activity_at; may dispatch panel events for agent.

--------------------------------------------------------------------------------
STEP 6 — Eloquent Created Hook Fires
--------------------------------------------------------------------------------
File    : ChatbotHistory.php
Method  : booted() -> static::created callback
Calls   : $history->detectAndStoreEnquiry()
Purpose : Side-effect detection after every history insert

IMPORTANT: This also fires for assistant/role messages, but step 7 exits early
unless role === 'user'.

--------------------------------------------------------------------------------
STEP 7 — Early Exit Guards Inside detectAndStoreEnquiry()
--------------------------------------------------------------------------------
File/Method: ChatbotHistory::detectAndStoreEnquiry()

Guard A: if role !== 'user' OR conversation_id missing -> return
Guard B: if conversation()->first() is null -> return

--------------------------------------------------------------------------------
STEP 8 — Build Detection Window Of User Histories
--------------------------------------------------------------------------------
Same method:

  $latestEnquiry = $conversation->enquiries()->latest('id')->first();

  $histories = $conversation->histories()
      ->where('role', 'user')
      ->when($latestEnquiry?->created_at, fn ($q) =>
          $q->where('created_at', '>=', $latestEnquiry->created_at))
      ->orderBy('id')
      ->get();

  Ensure current history is in collection (push if missing).

Purpose:
  After an enquiry exists, only consider user messages from that enquiry's
  created_at onward — so prior lead text does not keep re-triggering forever
  as one blob, and new leads can form from newer messages.

--------------------------------------------------------------------------------
STEP 9 — Incremental Candidate Window + Detector Executes
--------------------------------------------------------------------------------
Loop over histories chronologically:

  candidateHistories grows message by message
  detected = app(EnquiryDetectorService::class)->detect($candidateHistories)

File    : EnquiryDetectorService.php
Method  : detect()

Inside detect():
  1. buildUserMessageText() — join user messages with newline
  2. EmailDetector::detect($text)
  3. PhoneDetector::detect($text)
  4. CompanyDetector::detect($text)
  5. InterestDetector::detect($text)
  6. InterestDetector::countMatches($text)
  7. LeadScorer::score(...)
  8. is_enquiry = lead_score >= 50 (MINIMUM_ENQUIRY_SCORE)

--------------------------------------------------------------------------------
STEP 10 — Extracted Fields
--------------------------------------------------------------------------------
Returned keys:
  email, phone, company, interest, matched_keyword, lead_score, is_enquiry

If !is_enquiry -> continue loop (try larger candidate window)

--------------------------------------------------------------------------------
STEP 11 — Duplicate Check
--------------------------------------------------------------------------------
Lead identity for duplicate:
  email, phone, interest  (company NOT part of duplicate key)

Query:
  $conversation->enquiries()
    ->where(function ($query) use ($lead) {
        foreach email/phone/interest:
          null  -> whereNull(column)
          value -> where(column, value)
    })->exists();

If duplicate:
  reset candidateHistories = collect()
  continue (do not create)

--------------------------------------------------------------------------------
STEP 12 — Enquiry Created
--------------------------------------------------------------------------------
$conversation->enquiries()->create([
  chatbot_id,
  chatbot_customer_id,
  email, phone, company, interest,
  lead_score,
]);

Notes:
  - status defaults to 'new' at DB level
  - notes defaults to null
  - Method returns immediately after first successful create in the loop

--------------------------------------------------------------------------------
STEP 13 — Exception Handling
--------------------------------------------------------------------------------
Any Throwable in detectAndStoreEnquiry is caught:
  Log::warning('Chatbot enquiry detection failed.', [...])
Chat UX continues normally.

--------------------------------------------------------------------------------
STEP 14 — Admin Opens AI Bot Enquiries
--------------------------------------------------------------------------------
Route GET dashboard/chatbot/enquiries
Controller ChatbotEnquiryController::index
Scopes by user's externalChatbots ids
Renders chatbot::enquiry.index

--------------------------------------------------------------------------------
STEP 15 — Dashboard Displays Enquiry Analytics
--------------------------------------------------------------------------------
Route GET dashboard/chatbot
Controller ChatbotController::index
Computes total/status counts + latest 10
Views: actions-grid card + enquiry-analytics include

--------------------------------------------------------------------------------
STEP 16 — Messages Drawer Shows Extracted Enquiry
--------------------------------------------------------------------------------
ChatbotService eager-loads enquiry
ChatbotConversationResource maps enquiry JSON
contact-info-tab-details.blade.php shows Alpine-bound Extracted Enquiry card
(Uses HasOne enquiry — one card per conversation in UI)

================================================================================

7.1 Orchestrator
----------------
Class  : App\Extensions\Chatbot\System\Services\Enquiry\EnquiryDetectorService
Method : detect(ChatbotConversation|Collection $source): array
Constant: MINIMUM_ENQUIRY_SCORE = 50

7.2 How Email Is Detected
-------------------------
Class/Method: EmailDetector::detect(string $text): array
Pattern     : /[A-Z0-9._%+\-]+@[A-Z0-9.\-]+\.[A-Z]{2,}/i
Behaviour   : First regex match; returns {email, found}
Not used    : DNS validation, disposable email lists, etc.

7.3 How Phone Is Detected
-------------------------
Class/Method: PhoneDetector::detect(string $text): array
Patterns:
  INTERNATIONAL_PHONE_PATTERN
    (?<!\w)\+(?:\d[\s().-]?){7,15}\d(?!\w)
  LOCAL_PHONE_PATTERN
    (?<![\d+])(?:\d[\s().-]?){9}\d(?!\d)
Order: international first, then local
Normalize: keep leading '+', strip non-digits otherwise via normalizePhone()

7.4 How Company Is Detected
---------------------------
Class/Method: CompanyDetector::detect(string $text): array
Patterns tried in order:
  1) COMPANY_SUFFIX_PATTERN — capitalized words ending with
     Pvt Ltd / Private Limited / Ltd / Inc / LLP
  2) COMPANY_CONTEXT_PATTERN — after words company|organization|
     organisation|business|firm ...
cleanCompanyName() trims trailing conversational words.

7.5 How Interest Is Detected
----------------------------
Class/Method: InterestDetector::detect(string $text): array
Keyword groups (first match wins, group order matters):

  Pricing     : pricing, price, quotation, quote, cost
  Sales       : buy, purchase, subscription, plan, enterprise
  Demo        : demo, trial, testing
  Integration : integration, api, website, embed
  Support     : issue, help, support
  Callback    : contact, call me, callback, reach me

Matching: word-boundary regex case-insensitive via containsKeyword()

countMatches(): counts every keyword hit across all groups (used for bonus)

7.6 How Lead Score Is Calculated
--------------------------------
Class/Method: LeadScorer::score(...): array
Weights:
  email found                 +30
  phone found                 +30
  company found               +10
  interest found              +20
  interestKeywordCount > 1    +10
Cap: min(score, MAX_SCORE=100)

Examples that qualify (score >= 50):
  email + phone                 = 60
  email + interest              = 50
  phone + interest              = 50
  email + company + interest    = 60
  interest alone                = 20  (NOT enquiry)
  email alone                   = 30  (NOT enquiry)
  phone + company               = 40  (NOT enquiry)

7.7 Duplicate Prevention
------------------------
Location: ChatbotHistory::detectAndStoreEnquiry()
Scope   : Same conversation only
Key     : email + phone + interest (null-safe equality)
Not key : company, lead_score, status, notes
Action  : If exists -> skip create; reset candidate window; continue loop

7.8 Multiple Enquiries In Same Conversation
-------------------------------------------
After creating enquiry A, later user messages use histories with
created_at >= latestEnquiry.created_at.
A new combination of email/phone/interest can create enquiry B.
Exact same combination is ignored.

7.9 Same Enquiry Updated Or Ignored?
------------------------------------
Current implementation does NOT updateOrCreate.
It either:
  - creates a new row, or
  - skips as duplicate
There is no merge/update of an existing enquiry from detection.
Admin can PATCH status/notes via controller update().

15. MULTIPLE ENQUIRY LOGIC
================================================================================

15.1 Schema Allows Many Rows Per Conversation
---------------------------------------------
No unique on conversation_id.

15.2 Application Logic
----------------------

One Conversation
       |
       +--> Enquiry #1 (first qualifying lead combo)
       |
       +--> (same combo again) --> IGNORE (duplicate)
       |
       +--> Enquiry #2 (different email/phone/interest combo)
       |
       +--> Enquiry #N ...

15.3 How New Enquiries Are Identified
-------------------------------------
1. Load user histories since latest enquiry created_at (inclusive window)
2. Grow candidateHistories message-by-message
3. Run detector on concatenated candidate text
4. When is_enquiry true:
     Compare lead {email, phone, interest} to existing enquiries on conversation
5. If not duplicate -> create new row and return
6. If duplicate -> clear candidate window and continue scanning later messages

15.4 Why Candidate Window Resets On Duplicate
---------------------------------------------
Prevents the growing window from remaining "stuck" on an already-saved lead
while still allowing later distinct lead combinations to accumulate fresh
context from subsequent messages.

15.5 Messages UI Implication
----------------------------
Messages "Extracted Enquiry" uses HasOne enquiry().
Laravel HasOne does not automatically mean "latest".
Listing page shows ALL enquiries (HasMany reality).
Developers should be aware: drawer may not list every enquiry row for a
conversation — only the HasOne-loaded relation.

15.6 Historical Note (From Commit History)
------------------------------------------
Earlier implementations used updateOrCreate on conversation_id
(one enquiry per conversation). Current code (commit "multiple enquiries
in single chat") uses enquiries()->create() with duplicate checks.

18. SECURITY
================================================================================

18.1 Authorization
------------------
- Dashboard routes behind middleware web + auth
- No dedicated ChatbotEnquiryPolicy class found
- Ownership enforced by:
    whereIn('chatbot_id', auth()->user()->externalChatbots()->pluck('id'))
  on index/update/destroy
- update/destroy re-fetch with ownership or firstOrFail (404/ModelNotFound)

18.2 Validation
---------------
update():
  status required + Rule::in(new,contacted,qualified,closed)
  notes nullable string max 5000
index filters:
  allow-list checks rather than hard validation errors

18.3 Mass Assignment
--------------------
ChatbotEnquiry $fillable explicitly lists allowed columns.
Detection create only passes intended fields.
Admin update only passes validated status/notes.

18.4 SQL Injection Prevention
-----------------------------
Eloquent parameter binding used throughout.
Search uses where('col', 'like', "%{$search}%") with bound values via query builder
(standard Laravel binding — not raw interpolated SQL for values).

18.5 Duplicate Prevention
-------------------------
Application-level only; race conditions possible under concurrent writes
(no DB unique constraint). Acceptable for current sync request model.

18.6 CSRF
---------
PATCH/DELETE forms include @csrf (and @method spoofing).

18.7 API Message Path
---------------------
Public chatbot API creates histories; detection inherits that trust boundary.
Enquiry rows always copy chatbot_id from conversation (cannot spoof another bot
via detection payload because there is no public enquiry write API).

19.1 Detection Errors
---------------------
detectAndStoreEnquiry wraps logic in try/catch (Throwable).
On failure:
  Log::warning('Chatbot enquiry detection failed.', [
    chatbot_history_id, conversation_id, message
  ])
Does not rethrow — visitor chat continues.

19.2 Null Checks
----------------
- role must be user
- conversation_id required
- conversation model must exist
- empty detector fields become null via ?: null
- duplicate uses whereNull for null fields

19.3 Validation Errors (Admin Update)
-------------------------------------
Laravel validation exceptions redirect back with errors (standard framework).

19.4 Ownership Miss
-------------------
firstOrFail() raises ModelNotFoundException -> 404

19.5 Confirm On Delete
----------------------
Browser confirm() before DELETE submit (client-side only; not a server guard).

19.6 Logging
------------
Only explicit enquiry logging found: detection failure warning above.
Successful creates are not specially logged.

21.1 ChatbotHistory::booted / detectAndStoreEnquiry
---------------------------------------------------
WHY IT EXISTS:
  Central hook so every history insert path (storeMessage, appendMessage, etc.)
  automatically participates without duplicating detection calls.

WHO CALLS IT:
  Eloquent framework on ChatbotHistory::create / query()->create.

WHAT IT RETURNS:
  void (side effects only).

NEXT IN EXECUTION:
  EnquiryDetectorService::detect OR early return OR Log::warning.

KEY BRANCHES:
  1) non-user -> return
  2) no conversation -> return
  3) loop candidates -> detect
  4) not enquiry -> continue
  5) duplicate -> reset + continue
  6) create + return

23. INTERVIEW QUESTIONS (30) WITH IDEAL ANSWERS
================================================================================

Q1. Why was a service layer used instead of putting detection in the controller?
A1. Controllers handle HTTP. Detection is reusable domain logic (regex + scoring)
    that must run from a model event, not from an admin controller. Services keep
    SRP and testability.

Q2. Why not put all detection inside ChatbotEnquiryController?
A2. That controller is for admin CRUD. Detection must run on public chatbot
    message creation, which never hits EnquiryController.

Q3. Where is the detector called?
A3. ChatbotHistory::detectAndStoreEnquiry(), invoked from the Eloquent
    created hook in booted().

Q4. Why use an Eloquent model event instead of calling the detector in
    ChatbotApplicationController?
A4. Multiple code paths create histories (storeMessage, appendMessage, others).
    Hooking create ensures consistent coverage without missing a path.

Q5. Why HasMany enquiries and also HasOne enquiry?
A5. HasMany supports multiple leads per conversation. HasOne feeds the existing
    Messages UI which displays a single Extracted Enquiry card.

Q6. How does duplicate prevention work?
A6. Before create, query conversation enquiries for the same email+phone+interest
    with null-safe comparisons. If exists, skip create and reset candidate window.

Q7. Why is company not part of the duplicate key?
A7. Current code only compares email, phone, interest. Company can differ without
    creating a new identity under this rule.

Q8. How is lead score calculated?
A8. LeadScorer: email+30, phone+30, company+10, interest+20, +10 if more than one
    interest keyword match; capped at 100. Threshold 50 in EnquiryDetectorService.

Q9. What happens if detection throws an exception?
A9. Caught as Throwable; Log::warning; chat flow continues; no enquiry written.

Q10. How is authorization enforced on the listing?
A10. Auth middleware plus whereIn chatbot_id of the user's externalChatbots.
     update/destroy re-check ownership with firstOrFail.

Q11. Is there a Policy for ChatbotEnquiry?
A11. No dedicated Policy class in the implementation; ownership is query-scoped.

Q12. Does delete remove the conversation?
A12. No. Only the enquiry row is deleted.

Q13. Can a deleted enquiry reappear?
A13. Yes, if a later user message qualifies again, because the duplicate row
     no longer exists.

Q14. How are multiple enquiries in one conversation possible?
A14. No unique DB constraint on conversation_id; create() inserts new rows;
     windowing after latest enquiry allows new combinations.

Q15. How does incremental detection across messages work?
A15. candidateHistories grows message by message; detector runs on concatenated
     user text each time until a non-duplicate enquiry is created.

Q16. Why minimum score 50?
A16. Prevents weak signals (interest-only=20, email-only=30) from becoming leads.
     Contact + intent combinations typically meet 50+.

Q17. How is interest detected?
A17. InterestDetector keyword groups with word-boundary regex; first matching
     group label wins (Pricing, Sales, Demo, Integration, Support, Callback).

Q18. How is phone normalized?
A18. PhoneDetector::normalizePhone keeps optional leading +, strips non-digits.

Q19. What middleware protects enquiry admin routes?
A19. web + auth on the dashboard chatbot route group in ChatbotServiceProvider.

Q20. What is the route name for the listing?
A20. dashboard.chatbot.enquiries.index

Q21. How does the Messages UI get enquiry data?
A21. ChatbotService eager-loads enquiry; ChatbotConversationResource maps it to
     JSON; Alpine reads activeChat.enquiry.

Q22. Is Livewire used for this feature?
A22. No. Blade forms for listing; Alpine.js for Messages drawer.

Q23. How would you make detection more scalable?
A23. Queue a job from the created hook; batch process; add caching for repeated
     texts; move heavy NLP to workers (see Future Improvements).

Q24. Why fillable on ChatbotEnquiry?
A24. Mass assignment protection; only intended columns can be written via create/update.

Q25. What foreign key deletes cascade?
A25. Deleting chatbot or conversation cascades to enquiries. Deleting customer
     nulls chatbot_customer_id.

Q26. How are dashboard analytics computed?
A26. ChatbotController::index counts and groups statuses for owned chatbot_ids
     and loads latest 10 with customer.

Q27. What happens to assistant messages?
A27. History is created, hook runs, early return because role !== 'user'.

Q28. How would you improve duplicate prevention under concurrency?
A28. Add a unique composite index or use DB transaction with lock; currently
     application-level exists() check only.

Q29. Why keep detectors as separate classes?
A29. Single responsibility, easier unit tests, replaceable extractors without
     touching persistence.

Q30. If asked "how would you improve this feature tomorrow?"
A30. Queue detection; show all enquiries in Messages UI (HasMany); NER/ML for
     company/interest; audit log; unique constraints; metrics/alerts on detection
     failures; export CSV from listing.

24. FUTURE IMPROVEMENTS
================================================================================

Realistic improvements grounded in current architecture:

1) Queue Workers
   Dispatch DetectEnquiryJob from created hook to keep chat latency low.

2) Events / Listeners
   Emit EnquiryCreated event for CRM webhooks, email notifications, Slack.

3) Batch Processing
   Nightly re-scan conversations with improved detectors without blocking UX.

4) ML / NER Extraction
   Replace regex company/interest with NER models; keep LeadScorer interface.

5) Caching
   Cache detector results per message hash for retries/replays.

6) Performance
   Index (chatbot_id, created_at), (conversation_id, created_at);
   avoid loading full history collections for very long chats (window limits).

7) Scalability
   Horizontal workers; idempotent job keys; unique DB constraints for duplicates.

8) UI Enhancements
   Show all enquiries in conversation drawer; timeline of leads;
   bulk status updates; CSV export.

9) Observability
   Structured success metrics; alert on rising Log::warning rates.

10) Security Hardening
    Dedicated Policy; rate-limit admin deletes; redact PII in logs.

25. CONCLUSION
================================================================================

AI Bot Enquiries turns unstructured chatbot user messages into structured,
scored, manageable leads inside the existing MagicAI Chatbot Extension.

Architecture in one sentence:
  User message persistence triggers synchronous detection services that may
  insert rows into ext_chatbot_enquiries, which are then managed via an
  authenticated dashboard listing and surfaced on the chatbot home analytics
  and Messages Extracted Enquiry card.

Implementation pillars that actually exist today:
  - Table ext_chatbot_enquiries with FK cascades and notes
  - Model ChatbotEnquiry + relationships on Conversation/Customer/History hook
  - EnquiryDetectorService and five supporting detector/scorer classes
  - ChatbotEnquiryController index/update/destroy with ownership scoping
  - Routes under dashboard.chatbot.enquiries.*
  - Menu item ext_chatbot_enquiries
  - Blade listing + analytics + Alpine Extracted Enquiry card
  - Multi-enquiry create path with email+phone+interest duplicate guard
  - Fail-soft logging that never breaks the visitor chat path

A new developer should be able to:
  1) Trace a message from API storeMessage to enquiry insert
  2) Explain scoring and threshold 50
  3) Explain multi-enquiry vs Messages HasOne display
  4) Operate the admin listing (filter, update, delete, open conversation)
  5) Answer architecture questions without inventing non-existent queues,
     Livewire components, or updateOrCreate behaviour

End of document.
